# Flipper — Полный обзор проекта

> **Что это:** аналитическая платформа для рынка недвижимости Москвы. Цель —
> находить квартиры для классического флиппинга (покупка дешевле рынка → ремонт →
> продажа дороже). Это бизнес-аналитика + data engineering, не классический
> маркетплейс.

> **Аудитория этого документа:** разработчик, продакт-менеджер, инвестор
> (или сам автор через полгода), который хочет понять проект за 20 минут.

---

## 1. Бизнес-домен

### Что такое флиппинг в недвижимости

```
Покупаешь квартиру ниже рынка (например, убитую, в дешёвом районе,
или "срочно" уезжающего собственника) →
  ремонт (500К-2М ₽) →
    продаёшь на 10-20% дороже →
      маржа = (новая цена) - (цена покупки) - (ремонт) - (налоги 6% НДФЛ) - (риелтор 3%)
```

В Москве реальная маржа — 5-15% (с учётом всех расходов и времени).
На объёме в 1-3М ₽ маржа = 50-450К за 3-9 месяцев.

### Почему это сложно

- **Нужно видеть ВСЕ объявления** — пропустил одну выгодную = упустил месячный заработок
- **Нужно сравнивать с похожими** — квартира за 8М в Хамовниках vs 8М в Кузьминках = разные рынки
- **Нужно знать историю** — "почему так дёшево? А другие в этом доме за сколько?"
- **Нужно фильтровать мусор** — 50% объявлений = фейки, риелторы, дубли

### Почему платформа, а не скрипты

Один человек не может просмотреть 5000 объявлений в день на CIAN + domclick + baza-winner.
С платформой — это агрегация, дедуп, кластеризация, алерты на "аномально дёшево".

- **Яндекс Недвижимость** (скудный API, нет реального BFF)
- **Банкротство/торги** (отдельный рынок, не пересекается)
- **Реальные сделки из ЕГРН** (закрытый API, дорого)

## 3. Анализ через 5 lens-ов (deep-think-analyst framework)

### 3.1 Contrarian View: "где толпа ошибается?"

**Популярное мнение в нише:** "нужен ML на табличных данных, чтобы предсказывать цену продажи".
**Контр-тезис:** в нише флиппинга **главный bottleneck — не ML, а скорость получения данных и фильтрация мусора**.

> Один удачный парсинг + простой SQL-скрипт "все квартиры, где цена на 15% ниже медианы по кластеру за последние 60 дней" = уже продукт.

ML нужен только для:
- Предсказать цену продажи (по аналогам)
- Классифицировать "адекватный продавец" vs "истерик" (по описанию)

### 3.2 Systems View: где петли обратной связи?

```
+-- parsers (ежедневно) --+
|                        |
v                        |
[PostgreSQL: 270k снятых] --[синк]--> [Grist: 10 таблиц] --[read]--> [Next.js UI]
^                        |                                              |
|                        |                                              v
+-- houses + filters <----+                                         [Пользователь]
        ^                                                             |
        +------ "этот дом — фейк, удали" ---(по фидбэку)-------+
```

**Слабые петли:**
- ❌ Нет обратной связи от пользователя → нет self-improving моделей
- ❌ Парсеры не адаптируются к изменениям на CIAN
- ✅ Есть feedback на cookies (cookie_manager автоматически логинится при 403)

**Сильные петли:**
- ✅ Sync PG → Grist → UI: данные видны пользователю в реальном времени
- ✅ Alerts в Telegram при деактивации (мотивация к реагированию)

### 3.3 Evolutionary View: что отбирает?

**Что выжило:**
- Flippercrawl (self-hosted) — без зависимости от внешних SaaS
- PostgreSQL вместо SQLite — потому что SQLite не держит 300k+ строк
- Grist вместо Google Sheets — потому что Sheets API слишком медленный
- Pydantic вместо dataclass — потому что нужна валидация от внешних API
- rawData JSON в БД — потому что схема Cian меняется, а перепарсивать 270k записей дорого

**Что умерло:**
- _tmp_archive/parser_cian_legacy/ — прямой HTML-парсинг Cian (нестабильно)
- _tmp_archive/sheets_py_legacy.py — Google Sheets
- _tmp_archive/filters_page/ + pipeline_page/ + settings_page/ — Next.js pages
- Сейчас умирает: domclick cookies (если не обновить, парсер не взлетит)

### 3.4 Psychological View: когнитивные искажения

**Парсеры:** confirmation bias — "если URL содержит sale-flat, значит активное объявление"
→ Приводит к false positives (продано, но URL не изменился)

**Аналитика:** anchoring — "первая цена, которую я вижу, становится baseline"
→ Скрапинг должен показывать "а сколько этот же дом продавался 2 года назад?"

**Пользователь:** scarcity bias — "срочно, последняя квартира за 8М!"
→ Нужно явно показывать "есть ещё 3 похожих за 7.5-8.5М, не торопись"

### 3.5 Future View: что будет через 5 лет?

**Вероятный сценарий (70%):**
- CIAN ужесточает анти-бот → Flippercrawl приходится менять прокси каждый месяц
- AI extraction (LLM) делает custom scraping менее нужным
- Платформа эволюционирует: меньше parsing, больше analytics-as-service

**Менее вероятный (20%):**
- CIAN выкатывает официальный API для партнёров → scraping больше не нужен
- Вход в нишу для всех желающих

**Black swan (10%):**
- Недвижка в Москве обваливается → спрос на флиппинг исчезает
- Регуляторы запрещают агрегацию объявлений

## 4. Технический долг (с приоритетами)

### 🔴 Блокеры (мешают прямо сейчас)

1. **Двойная схема БД** (active_ads vs cian_active_ads) — парсеры пишут в legacy
   - Решение: либо мигрировать парсеры на новую схему, либо оставить legacy-only
2. **Stale domclick cookies** — Qrator 403
   - Решение: cookie_manager должен поддерживать domclick cookies

### 🟡 Важно (мешает росту)

4. **Нет алгоритма скоринга "выгодности"** — только raw данные
5. **Sync PG → Grist** — медленный, sync только дельты не сделан
6. **Нет self-healing cookies** — если куки сломались, ждём пока юзер починит руками
7. **Backup-стратегия** — `dump_local_pg_to_csv.py` есть, но не автоматизирован

### 🟢 Пожелания (nice to have)

8. **Авито-парсер** (открывает +30% рынка)
9. **ML-модель предсказания цены продажи**
10. **Публичный API** (для интеграции с CRM риелтора)

## 6. Ключевые инсайты для разработчика

> "Что я хотел бы знать, начиная работу над проектом с нуля."

1. **Сырые данные в rawData JSON — это страховка.** Схема Cian меняется каждый месяц.
   Если хранить только распарсенные колонки, через год половина полей будет "неизвестно".

2. **Grist — это не "таблица", а формат-обёртка.** У Grist есть SQL-движок под капотом (SQLite).
   Можно делать `SELECT * FROM Sold_Ads WHERE status='deactivated'` через REST API.
   Это делает Grist де-факто OLAP-движком для бэкенда.

3. **Двойная схема БД — это не баг, это фича.** Парсер пишет в legacy (cian_active_ads),
   sync-script переносит в новую (active_ads). Это даёт "транзакционную" изоляцию
   между быстро меняющимися данными парсера и стабильными данными для UI.

4. **Cookie_manager — критическая зависимость.** Если он упадёт, все парсеры встанут.
   Должен быть monitoring + auto-restart (через Docker restart policy).

5. **Flippercrawl в Docker = single point of failure.** Сейчас он standalone, но если 50 воркеров
   одновременно дёрнут /v2/cian/scrape, queue может захлебнуться. Нужен rate limiter.

6. **Ручные парсеры (заархивированные) — это страховка, не легаси.** Если автоматика
   упадёт (CIAN изменит вёрстку, cookie-rotate не сработает), есть fallback
   на ручной запуск с сохранённым кодом.
